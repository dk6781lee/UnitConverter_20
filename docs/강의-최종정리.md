## 2. 핵심 개념 한 장

| 개념 | 한 줄 |
|------|------|
| **C2C** | 개념·요구 → 테스트 → 코드까지 **추적 가능**하게 (체계화) |
| **바이브 코딩** | **동작** 맞춤 — 돌아가면 OK, 추적·검증 약함 (카파시) |
| **C2C 코딩** | **문제(요구)** 맞춤 — 정의한 요구를 테스트로 증명 |
| **PCTF** | **P**ersona · **C**ontext · **T**ask · **F**ormat — 구조화 프롬프트 |
| **프롬프트→컨텍스트→하네스** | 점점 넓어지는 동심원 · C2C 담보 힘도 커짐 |
| **ARRR** | Ask · Respond · Refine · Repeat |
| **Dual-Track TDD** | Track A(UI/Boundary) + Track B(Domain/Entity) |
| **ARRR ≡ Dual-Track TDD** | 같은 것의 다른 이름 (별개 아님) |
| **7단계** | ①주제 ②설계 ③④⑤⑥=ARRR ⑦확장 |
| **ECB** | Boundary(창구) · Control(조율) · Entity(순수 로직) |
| **IPO** | Input → Process → Output 모듈 설계 (R-G-I-O와 목적 다름) |
| **Spike** | 불확실할 때 **짧은 탐색 실험** → 버린 뒤 정식 RED (교재 외·수업 언급) |

## 3. 바이브 vs C2C vs PCTF

| | 바이브 | PCTF | C2C |
|---|--------|------|-----|
| 초점 | 일단 **돌아가게** | **말을** 구조화 | **요구·개념**이 코드와 **안 어긋나게** |
| 코드 | diff 안 봄·Accept | Format에 출력 규정 | PRD↔TC↔코드 **역추적** |
| 검증 | 약함 | Task·Format에 테스트 요구 가능 | **pytest = 판정** |
| 적합 | 버릴 프로토타입 | 매번 쓰는 프롬프트 | 실무·팀·유지보수 |

> **바이브 = 동작 맞춤 · C2C = 문제(요구) 맞춤 + 추적**

## 4. C2C 추적성 4계층 (위→아래 검증)

| Layer | 내용 | 예 (Magic Square) |
|-------|------|-------------------|
| 1 Invariant | 절대 바뀌면 안 되는 진실 | 4×4 합=34, 1~16 한 번씩 |
| 2 UI Contract | 입력·출력·에러 계약 | E001~E007, int[6] 형식 |
| 3 Domain | 비즈니스·알고리즘 규칙 | 빈칸 찾기, 마방진 판정 |
| 4 Unit | 구현 단위 | 순수 함수·엔티티 |

**태도**: 테스트 없는 코드 = 추적 불가 → 제거 대상.

**추적 경로**: `PRD → To-Do → Test Case → 코드 → Report`

## 5. ARRR · TDD · 7단계

### TDD ↔ ARRR

| TDD | ARRR | 하는 일 |
|-----|------|---------|
| RED | **Ask** | 실패 테스트로 질문 · **구현 금지** |
| GREEN | **Respond** | 최소 구현으로 PASS · 1 RED = 1 커밋 |
| REFACTOR | **Refine** | PASS 유지하며 정리 · 계약 변경 금지 |
| 다음 RED | **Repeat** | 문서화 후 다음 질문 (최소 3회) |

### 7단계 (Magic Square / UnitConverter)

| 단계 | 내용 | 세션 |
|------|------|------|
| ① 주제 | Mom Test · 좋은 주제(명확 I/O) | D1 세션 3 |
| ② 설계 | R-G-I-O · Cursor 8계층 구성 | D1 세션 3 |
| ③ Ask | RED 설계·스켈레톤 | D1 세션 4 |
| ④ Respond | GREEN | D1 세션 4 |
| ⑤ Refine | REFACTOR · Golden Master | D1 세션 4 |
| ⑥ Repeat | Report 8섹션 · Transcript | D1 세션 5 |
| ⑦ 확장 | 새 기능 = 새 ARRR | D1·D2 |

### Ask(RED) 핵심 규칙

- `pytest` → **의도적 FAIL** (`pytest.fail("RED: ID")` OK)
- `src/` 수정 금지 · skip/xfail 금지
- PRD FR ↔ Test ID 매핑 (C2C)
- Cursor: **Ask 모드** + `/red-test-plan` → `/red-skeleton`

### Dual-Track

| Track | 역할 | 테스트 |
|-------|------|--------|
| **A Boundary** | 입력·에러·출력 | `tests/boundary/` · Domain Mock |
| **B Domain** | 규칙·알고리즘 | `tests/entity/` · Mock 없음 |

### 브랜치 전략

```
main
└ staging
   ├ spec
   ├ red
   ├ green
   ├ refactoring
   └ new_features
```

## 6. 의도 전달 3단계 · Cursor 대응

| 단계 | 질문 | Cursor |
|------|------|--------|
| **프롬프트** | 어떻게 말할까? | Chat 한 번 · PCTF |
| **컨텍스트** | 무엇을 보여줄까? | @PRD · @파일 · Rule · Skill · MCP |
| **하네스** | 어떻게 일하게? | Agent 루프 · Tool · Command · **pytest 루프** |

**Agent = Model + Harness** — LLM은 엔진, 하네스가 일하게 만듦.

## 7. Cursor 기술 체계 (8계층 + Hook)

| # | 계층 | 역할 |
|---|------|------|
| 1 | Model | 추론·코드 생성 |
| 2 | Agent | 실제 작업 (Ask vs Agent) |
| 3 | Harness | 실행 환경 (`src/`·`tests/`·pytest) |
| 4 | Rule | 항상 지키는 헌법 (`.cursorrules`) |
| 5 | Skill | 절차 매뉴얼 (필요 시만) |
| 6 | Command | `/tdd-red` 등 PCTF 프롬프트 `.md` |
| 7 | Tool/MCP | Shell · Read/Write · GitHub 등 |
| 8 | Test/Review Loop | **pytest = 최종 판정** |

**Hook** = 깜빡임·우회 방지 자동문 (힌트·차단) — **판정은 pytest가 함**.

**분담**: Rule/Hook = 안내·차단 · Test Loop = PASS/FAIL.

## 8. AI 문서화 (C2C 마지막 고리)

### 3원칙

1. **SSOT** — 요구는 `docs/PRD` 한 곳
2. **세션 = 저장 단위** — ARRR 한 바퀴마다 Report + Transcript
3. **번호 일관성** — `Report/01.md` …

### Report 8섹션

1. 작업 개요 · 2. 완료 To-Do · 3. RED · 4. GREEN · 5. REFACTOR  
6. 커버리지 · 7. 미완료·다음 단계 · 8. 이슈·결함

→ **개념→코드→결과** 추적 기록으로 C2C가 문서로 닫힘.

## 10. 2일차 (D2) 흐름 요약

| 시간 | 세션 | 핵심 |
|------|------|------|
| 오전 | Ground Rules | 팀·코드리뷰 그라운드 룰 · 점진적 개선 |
| 오전~오후 | UnitConverter 실습 | PRD 기반 재구현 · C2C · ARRR 1사이클 |
| 오후 | 팀 리뷰 | PRD→TC→코드 추적 확인 · main 병합 전 게이트 |
| 마무리 | KPT 회고 | C2C 질문 · 현업 Action Item |

### UnitConverter 핵심

- **목표**: 레거시 37줄 → PRD·테스트 추적 가능한 CLI
- **입력**: `meter:2.5` · **품질**: OCP · SRP · 검증
- **시드 문제**: if/elif 분기 · 하드코딩 · SRP 위반 → **RED로 갭 메우기**
- **구조**: Parser · Registry · Converter · Formatter 분리
- **필수**: 기본+품질+Domain TC · **팀 리뷰**에서 AI 코드 설명 + C2C 확인

### Ground Rules 요지

- 합의·5개 내외·구체적·예외 없음·주기적 리마인드
- 코드 리뷰: 린터 자동화 · 원칙 기반 · 200 LOC 이하 · 범위 존중 · 칭찬

### KPT

| K | P | T |
|---|---|---|
| 잘 된 것 유지 | 문제 | **Try = Action Item** |

진행: Check-In(3분) → Post-it(15분) → 그룹핑·Try 선정(25분)

## 11. 설계·용어 보조 (대화에서 정리)

### R-G-I-O (프로젝트·AI 설계)

| | 의미 |
|---|------|
| Role | 사고방식·역할 |
| Goal | 만들 것 |
| Input | 예시 입력 |
| Output | 출력 형식 |
| 성공 기준 | → 나중에 **테스트 씨앗** (C2C 시작) |

### IPO (SW 모듈 설계)

**Input → Process → Output** — 한 모듈이 무엇을 받아 처리보내는지. R-G-I-O와 **다른 틀**.

### 테스트가 하는 일 (오해 바로잡기)

버그 잡기·커버리지 채우기만이 아님 → **설계 검증 · 리팩토링 안전망 · 살아 있는 문서 · 회귀 방지** (→ C2C).

## 12. pytest · 자주 쓰는 명령

```powershell
python -m pytest --collect-only -q
python -m pytest tests/ -v
python -m pytest tests/boundary/ -v    # Track A
python -m pytest tests/entity/ -v      # Track B
python -m pytest --cov=src --cov-report=term-missing
```

| Phase | 기대 |
|-------|------|
| RED | **FAILED** (의도적) |
| GREEN/REFACTOR | **passed** |
